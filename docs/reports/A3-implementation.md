## Design decisions (scrutinize)
1. **Routing**: `EspNetwork.openConnection` → `android.net.Network.openConnection(url,Proxy.NO_PROXY)`. There is no `bindProcessToNetwork` (a source-scan test enforces this). The laptop client keeps its unbound `URL.openConnection(Proxy.NO_PROXY)`. Every selection or address change makes a new `NetworkLease`. On a lease change, live calls are cancelled, results from the old epoch are discarded, and the queue is settled.
2. **Bridge lanes** (A1 file changed): the shared two-worker pool is replaced by one single-thread lane per transport operation. A 1.5–8-s controller stall therefore cannot delay or time out `hub.snapshot` (and vice versa). The router still allows one live request per operation.
3. **Serialized controller channel**: one fair semaphore for polls, history, writes and reconciliation reads, because the firmware serves one client at a time. Polls wait ≤4.5 s, writes ≤8 s. A sequence number stops an older observation from overwriting a newer one.
4. **esp.set** waits ≤7 s, then returns `pending` (below the 10-s bridge deadline). The terminal outcome arrives through `esp.state.commands`. Renderer teardown interrupts only the waiter; the Activity-owned unit continues and its outcome survives.
5. **Queue**: ordinary units dispatch 150 ms after creation, so latency is bounded during a drag, and keep merging until dispatch. Timer units dispatch at once. Dispatch starts are spaced ≥250 ms apart, so ≤4 per second. QUEUE_FULL is decided before any mutation. A failed state write gets exactly one reconciliation read begun after dispatch; there is no later upgrade and no retry. A failed timer stays unconfirmed with no read. The floor rule: only the newest generation of each kind updates `commands`. A confirmed later power-off turns an *unconfirmed* timer marker into `cancelled`, since the firmware clears the timer on power-off. `desired` holds the latest submitted values; observations never erase it, and loss or teardown clears it.
6. **Parser** (judgement calls): `timer` is clamped to 0..43200, because the firmware replies 43201 right after a 720-min set and ≤0 at expiry. Humidity outside 0–100 becomes null, so a sensor glitch never blocks controls. Known extra firmware keys are ignored; any other key is rejected. History is stale after 60 s, my choice since the protocol gives no threshold. A drop in uptime is a reboot: it is accepted, and the old history is dropped.
7. **Wi-Fi setup**: API 29/30 request FINE; API 31/32 request FINE+COARSE (31+ ignore a FINE-only request); API 33+ request NEARBY_WIFI_DEVICES (neverForLocation). With location services off on API 29–32, setup finishes failed with guidance *before* any request, and `beginOsApproval` is not used around the Location settings screen. `beginOsApproval` brackets only the runtime-permission dialog and the system network prompt, and ends at their results. Success requires controller HTTP on that lease (3 tries). Denial, unavailability or a wrong network finish setup failed and release the request, with no automatic re-prompt. Choosing manual finishes setup `cancelled` with `wifiMode:"manual"`, never a fake success. Foreground return re-requests only after a previous HTTP-verified success (persisted, so it survives process death).
8. **Normal permissions** added: ACCESS_NETWORK_STATE, CHANGE_NETWORK_STATE, CHANGE_WIFI_STATE. Whether CHANGE_WIFI_STATE is strictly needed is unverified on device.

## Known gaps
- `AndroidWifiPlatform`, `AndroidPermissionGate`, `PrivateWifiStore`, the Wi-Fi dialog and permission-result code are compiled and lint-checked but not executed; there is no new instrumentation test. Behaviour of Android's own per-network HTTP stack (cancel, Host header) is device-unrun.
- An address change (`onChanged`) is treated as loss: the in-flight command becomes unconfirmed and unsent commands are cancelled. In manual mode with several Wi-Fi networks, the most recently available one is leased.
- When the channel is busy, a write is reported as a failure. A state write then reconciles by read; a timer that was never sent is reported unconfirmed (safe, but it understates).
- Unknown future firmware keys would make state BAD_PAYLOAD (strict by design).
