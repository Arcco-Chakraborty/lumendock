# A-final — Android fixes from the final review

Status: software fixes complete. **No commit and no git writes** (the coordinator commits). **No device was attached**: these results are software verified, not device accepted. Edited only `android/**` and this report.

## Finding → change → test
1. **API 29 re-prompt on every onStart (Important, suspected).** `WifiStore` gains `pinnedBssid` and `pinFailed`, stored privately in `native_wifi` prefs next to the credentials and never put in a bridge reply. `WifiBssid.normalize` rejects null, redacted `02:00:00:00:00:00`, all-zero, broadcast, multicast and malformed values.
   - The `WifiPlatform` seam changed to `requestLocalNetwork(credentials, bssid?, callbacks)` and gained `accessPoint(network, ssid)`.
   - `WifiSession.markVerified(lease)` runs after the controller answers over HTTP. It pins the BSSID only if the lease is still the verified one. Later requests then call `setSsid` plus `setBssid(MacAddress)`.
   - A different SSID/passphrase clears the pin. A pinned request that is unavailable, or that throws, sets `pinFailed`. Automatic retries keep using the pin and never widen to SSID-only. The **next explicit setup** clears the pin and asks by SSID only, once.
   - Android side (`AndroidWifiPlatform`): the BSSID comes from the callback's `NetworkCapabilities.transportInfo` (`WifiInfo`). On API 31+ the request uses a `FLAG_INCLUDE_LOCATION_INFO` callback (`@RequiresApi(S)` class). On API 29/30 it falls back to `WifiManager.connectionInfo`, only when the SSID matches. That fallback has a localized `@Suppress("DEPRECATION")` and needs the new normal permission `ACCESS_WIFI_STATE` with `maxSdkVersion=30`.
   - **Prompt loop on automatic requests:** an automatic request cannot be tied to a setup ID, so I did not use `beginOsApproval` (A1 rule kept). Instead, a stop that comes less than 5 s after an automatic request, before it resolves, skips the auto-request on the next start once. This breaks any request→stop→start loop. A second `resume()` while still started is now a no-op.
   - Tests (`WifiFinalFixesTest`): `verifiedSetupPinsTheConnectedBssid…`, `redactedMissingOrInvalidBssidIsNeverPinned`, `pinIsTakenOnlyFromTheVerifiedLease…`, `pinnedFailureFallsBackToSsidOnlyOnce…`, `automaticRequestInterruptedByAStopRightAway…`. `NetworkSecurityConfigTest` was updated: 8 permissions, including `ACCESS_WIFI_STATE` max 30.
2. **One unavailable permanently cleared autoReconnect (Minor, proven).** `onUnavailable` now clears it only for an explicit (setup) request. An automatic request keeps the opt-in, releases its handle, and is retried only on the next `resume()` (onStart). Explicit denial, unavailability or a wrong password during setup still clear it, through the existing `fail()` → `disconnect()`. Tests: `unavailableOnAnAutomaticReconnectKeepsAutoReconnect…` and `unavailableDuringAnExplicitSetupStillClearsAutoReconnect`; the existing `unavailableOrDenied…` test still passes.
3. **Same-network LinkProperties change treated as loss (Minor, proven).** `onChanged`, and `onAvailable` for an already-leased handle, now keep the same `NetworkLease`. Only `onLost`, `onUnavailable` or a different handle change the lease. `Forwarder` no longer diffs addresses. `EspClient` itself is unchanged; its `NetworkLease` doc now states the contract. Test: `sameNetworkLinkOrCapabilityChange…` (WifiSession + real EspClient + gated fake transport) shows 0 cancels and that verify still succeeds. **Changed existing assertion:** `WifiSessionTest.appRequestLeases…` used to assert "address change recreates the lease", which is the behaviour this fix removes. It now asserts `assertSame`.
4. **Unguarded `proxy.postMessage` on the delivery path (Minor, suspected).** The posted callback in `LifecycleReplyDelivery` is now wrapped in try/catch for `RuntimeException` (reply dropped; the pending slot was already released). The early `BAD_PAYLOAD` `postMessage` in `DashboardBridge` is guarded the same way. Test: `throwingReplyProxyIsDroppedWithoutEscapingThePostedDelivery`.
5. **`requestNetwork`/`registerNetworkCallback` can throw (Minor, suspected).** `WifiSession` catches every `RuntimeException` from the seam: no handle is held and nothing crashes. `connect()` now returns `WifiConnectResult` (STARTED / NOT_SAVED / REQUEST_FAILED); `REQUEST_FAILED` makes `WifiSetupFlow` fail the setup with `WIFI_UNAVAILABLE` and the UNAVAILABLE message. An automatic request that throws keeps autoReconnect for the next start. If observing throws in manual mode, the mode stays manual with no lease. Tests: `throwingPlatformNeverCrashesStartOrManual…` and `throwingRequestDuringExplicitSetupFailsWithWifiUnavailable` (SecurityException, IllegalArgumentException, RuntimeException).

## Residual risks (device-only, UNRUN)
- It is unverified that Android 10/MIUI really skips the prompt for SSID+BSSID of an approved AP. Also unverified: that `WifiManager.connectionInfo` on API 29/30 reports the specifier network's BSSID (it needs location permission plus Location on, both already enforced by setup), and what `transportInfo` contains on API 30.
- On API 33+, NEARBY_WIFI_DEVICES (neverForLocation) probably yields a redacted BSSID. Then nothing is pinned and behaviour is as before.
- If no pin exists and a system approval Activity stops the app during an automatic request, the loop guard stops the loop, but that start ends without a connection; the user reconnects explicitly. A genuine Home press within 5 s of an automatic request also skips one automatic retry.
- An automatic request that was cancelled by the user (if Android shows UI) is indistinguishable from "unavailable". It is retried once per later onStart.
- If the controller's MAC changes, automatic pinned requests keep failing silently until the user runs an explicit setup.
