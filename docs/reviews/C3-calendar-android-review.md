## Review evidence

Inspected the C3 brief, frozen C1 schemas/fixtures, C3 report, snapshot-relative diff (`task-3-diff.md`), JUnit XML reports, and current Android source files with line numbers:

- `android/app/src/main/java/com/phonemonitor/CalendarValidator.kt` (`1–285`):
  - **Gregorian dates (`CalendarValidator.kt:17, 69–107`):** Enforces 10-character ASCII `YYYY-MM-DD` (`[0-9]{4}-[0-9]{2}-[0-9]{2}`, rejecting full-width Unicode digits), `year >= 1`, `month in 1..12`, and exact leap-year rules (`year % 4 == 0 && (year % 100 != 0 || year % 400 == 0)`), matching `packages/protocol/src/calendar.ts:9–16`.
  - **IANA time zones (`CalendarValidator.kt:19, 109–114`):** Enforces 1–80 code points, rejects leading `+`/`-` fixed offsets, and checks membership in `ZoneId.getAvailableZoneIds().toSet() + "UTC"` (which excludes bare `GMT+...`/`UTC+...` offset strings while permitting canonical IANA zones such as `UTC`, `Asia/Kolkata`, `America/New_York`, and `Etc/GMT+5`), matching `calendar.ts:17–21`.
  - **Identifiers, cursors, colors, and code-point limits (`CalendarValidator.kt:15–18, 48–61`):** Enforces `[A-Za-z0-9_-]{1,80}` for opaque IDs/revisions, `[A-Za-z0-9._~-]{1,256}` for cursors, `#[0-9a-fA-F]{6}` for hex colors, and Unicode code-point limits via `String.codePointCount(0, length)` (`title <= 256`, `calendarName <= 120`, `source.name <= 120`, `label.name <= 50`, `eventType <= 40`).
  - **Requests (`CalendarValidator.kt:120–149`):** `rangeRequest` enforces `startDate`, `days` (`1..31`), `timeZone`, optional `cursor` and `refresh`, and rejects `refresh: true` combined with `cursor` (`!(o.has("refresh") && o["refresh"].asBoolean && o.has("cursor"))`). `sourcesRequest` enforces optional `cursor` only. `selectRequest` enforces `expectedRevision` and unique `sourceIds` capped at 100.
  - **States, errors, moments, events, and sources (`CalendarValidator.kt:21–38, 159–214`):** Closed `states` include `setup_required`; closed `errors` match the six `CALENDAR_*` codes and are unioned into `ProtocolValidator.errors` (`ProtocolValidator.kt:38`). `moment` discriminates `"date"` and `"time"` with strict key sets. `event` enforces matching `start`/`end` kinds and strictly positive duration (`start.date < end.date` or `start.epochMs < end.epochMs`), `status` in `confirmed | tentative` (rejecting cancelled rows), `selfResponseStatus` in `needsAction | declined | tentative | accepted | null`, and `reminderMinutes` in `0..40320 | null`. `normalizePage` (`CalendarValidator.kt:271–284`) normalizes empty `""` titles to `"Untitled event"` on both `items[]` and `nextEvent`.
  - **Pages and byte budgets (`CalendarValidator.kt:88–89, 216–268`):** Enforces `v == 1`, `sourceCount` and `failedSourceCount` in `0..100`, `sources` and `items` arrays capped at 50, 128 KiB (`131072` bytes) UTF-8 serialized byte budget (`PAGE_BYTES`), page `sources` coverage of every item's `sourceId` (`CalendarValidator.kt:237–239`), and `nextEvent` eligibility (`kind == "time"`, `selfResponseStatus != "declined"`, `end.epochMs > serverNowEpochMs`, without requiring `nextEvent.sourceId` to appear in the current page's `sources` subset, `CalendarValidator.kt:241–249`).
  - **Unknown-key rejection (`CalendarValidator.kt:40–46`):** Every object validator uses `obj(e, required, optional)` which enforces exact key sets and rejects any extra keys (URLs, tokens, emails, descriptions).

- `android/app/src/main/java/com/phonemonitor/CalendarClient.kt` (`1–495`) & `LaptopClient.kt` (`30–36, 128–168`):
  - **Fixed POST paths and transport reuse (`LaptopClient.kt:30–36`, `CalendarClient.kt:15–29, 178, 284, 370`):** Adds only fixed loopback POST paths `CALENDAR_READ` (`http://127.0.0.1:8765/v1/calendar/read`), `CALENDAR_SOURCES` (`http://127.0.0.1:8765/v1/calendar/sources`), and `CALENDAR_SELECT` (`http://127.0.0.1:8765/v1/calendar/select`). Reuses `LaptopClient`'s unbound `LoopbackHubTransport` (`Proxy.NO_PROXY`, no redirects, 2 s connect / 3 s read / 5 s call budget, `Connection: close`) and `PairingStore`. Enforces the 16 KiB (`BRIDGE_REQUEST_BYTES`) request body limit (`CalendarClient.kt:7, 157, 264, 359`).
  - **Native bearer confinement (`CalendarClient.kt:57–90, 433–469`):** Bearer stays in native storage and `Authorization: Bearer ...` headers; `HubRequest.toString()` omits it; `interpretPage`, `interpretSources`, and `interpretSelect` reject any response echoing the bearer (raw, re-cased, or Unicode-escaped) via `LaptopClient.containsSecret` on both raw response bytes and normalized JSON bytes. Transport exceptions never leak message strings into `LinkSnapshot` or `BridgeFailure`.
  - **Old-hub 404 compatibility (`CalendarClient.kt:420–421`):** Maps HTTP `404` on any calendar route to `CALENDAR_UNSUPPORTED` without touching `LaptopClient`'s snapshot cache or revoking native pairing.
  - **Bearer 401 vs Google grant errors (`CalendarClient.kt:180–184, 286–290, 396–401, 420–431, 486–494`):** Only an HTTP `401` carrying a strictly validated `{"v":1,"error":{"code":"AUTH_REQUIRED"}}` hub envelope produces `Outcome.Rejected`, and `revokeBearer(bearer)` revokes the token only if it still matches the current stored bearer (preventing a stale 401 from an old token from erasing a newly paired token). Domain-level `state: "auth_required"` / `CALENDAR_AUTH_REQUIRED`, HTTP 401 with `CALENDAR_AUTH_REQUIRED`, and unvalidated 401 bodies never revoke native laptop pairing.
  - **Independent caches and monotonic receipt-age baselines (`CalendarClient.kt:121–143, 222–260, 328–355`):** `pageCache` (max 12) and `sourcesCache` (max 8) are independent of `LaptopClient`. Each entry records `baselineMonoMs = nowMono - max(0, serverNowEpochMs - lastSuccessAtEpochMs)`. Transport/validation failures do not replace `CachedEntry`, and upstream `error`/`partial` pages where `lastSuccessAtEpochMs` is null or unchanged preserve `minOf(prev.baselineMonoMs, candidateBaseline)` so stale cached age continues advancing monotonically.
  - **Authoritative `select()` and race protection (`CalendarClient.kt:357–418`):** `select()` mutates state only after a validated HTTP 200 `{selectionRevision}` reply, increments `selectionEpoch`, updates `cachedSelectionRevision`, clears `pageCache` and `sourcesCache`, and cancels all in-flight `readAndSourceCalls`. Any pre-selection `read()` or `sources()` call checks `selectionEpoch == callSelectionEpoch` before storing data or error outcomes, preventing stale pre-selection reads from repopulating invalidated caches.
